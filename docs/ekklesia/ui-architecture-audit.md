## 1. Executive summary

- **church-cms has essentially no UI yet.** The entire user-facing surface is three screens: the default Create-Next-App landing page (`src/app/page.tsx`), one stand-alone admin screen for events (`src/app/events/`), and the Platform Operator console on its own subdomain (`src/app/platform/**`). There is **no application shell, no sidebar, no topbar, no auth-gated route group, no member portal, and no shared component library** anywhere in `src/app/**`. **[Confirmed]** — see §2.4 full route inventory.
- **Styling is near-zero.** `src/app/globals.css` is 27 lines of default Create-Next-App Tailwind v4 tokens (background + foreground + Geist fonts). The Platform console ships its own self-contained dark theme (`src/app/platform/platform.css`, `.platform-*` classes, 295 lines). The Events page ships a one-off cream/green theme **inline via `<style jsx global>`** inside the client component. No shared design tokens. **[Confirmed]**
- **Backend is large and mature; must not be touched by UI work.** `src/app/api/v1/**` contains ~130 REST route files across ~17 business modules (people, households, membership, events, attendance, finance, messaging, imports, governance, platform-ops, …). This is the surface the new UI will consume. **[Confirmed]** — see §2.5.
- **RentFlow is a rich structural donor.** It ships a fully articulated `rf-*` admin design system (sidebar + topbar + role-aware nav, ~27 Blade components, ~4,820 CSS lines across `app.css` + `app-ui.css` + `public.css`, and three design-system docs). The shipped Rent­Flow admin palette is **IBM Plex Sans + Proxima blue (`#1890ff`) / teal (`#13c2c2`) on `#f5f7fb`**, not the green/clay described in `docs/DESIGN_SYSTEM.md`. **[Confirmed]** — see §5 and §6.
- **Transformation is viable and low-risk.** Because church-cms has no legacy UI shell, none of the RentFlow patterns compete with existing work. There is no "Rent­Flow brand bleed" to clean up — the only visual debt is the default Next.js scaffold on `/` and the one-off inline themes on `/events` and `/platform`.

## 3. Application boundaries — current vs intended

### 3.1 Confirmed today

| Surface | Status today | Evidence |
|---|---|---|
| **Public / marketing** | Default Create-Next-App scaffold on `/`. Not a real surface. | `src/app/page.tsx` |

| **Admin app** (people, households, membership, ministries, events, attendance, projects, communications, finance, imports, governance) | Only `/events` exists, and it is a single ad-hoc page. **No shell, no sidebar, no cross-module navigation.** | `src/app/events/*` |
| **Member portal** | **Does not exist.** `src/app/api/v1/*/me/route.ts` endpoints (`auth/me`, `people/me`, `memberships/me`, `attendance/me`, `participation-requests/me`, `communication-preferences/me`, `events/[id]/registrations/me`, `pledges/unpaid`, …) are ready but **have zero client surface**. | File listing in §2.4, API list in §2.6 |
| **Platform operator console** | **Exists**, lives on an independent subdomain (`platform.localhost:3000` / `platform.<NEXT_PUBLIC_ROOT_DOMAIN>`), has its own layout + nav + dark CSS, wired to `/api/v1/platform/*`. | `src/app/platform/**`, `src/proxy.ts`, `docs/09-adr-0003-platform-operator.md` |

### 3.2 Intended (per `docs/AGENTS.md` and `docs/09-adr-0003-platform-operator.md`)

- Admin app and member portal are both expected inside the single Next.js app (modular monolith; backend extraction is a *later* possibility per `docs/07-backend-extraction.md`).
- Platform operator is **always on its own subdomain** (ADR-0003) and should retain its independent identity, not be absorbed into the admin shell. The current CSS boundary (`.platform-*` + `platform.css` scoped by `src/app/platform/layout.tsx`) is intentional and should be preserved during the transformation.
- Multi-church (multi-tenant) is in scope now at the API/data layer; UI must assume more than one church will eventually sign in, but the pilot is CrossLife only.

### 3.3 Implication for the transformation

- The admin shell and the member shell are **both greenfield**; they can be designed without migrating any existing screens.
- The Platform console is in scope only insofar as it should **optionally** adopt the same Ekklesia tokens without losing its "this is the platform operator, not a church admin" visual distinction. Treat it as a secondary adaptation, not a primary workstream.

## 11. Open questions for Lead Architect

1. **Route-group naming.** Confirm `(admin)` and `(member)` as the authenticated route groups, and `(auth)` for sign-in. Alternatives: `(app)/admin/*`, `(app)/member/*` nested. The flat sibling approach gives both experiences independent `layout.tsx` files, which simplifies the shell split.

3. **Platform console scope.** Treat it as (a) out-of-scope visual-wise, (b) skinned only (recoloured but unchanged structurally), or (c) fully rebuilt to Ekklesia tokens including nav structure? ADR-0003 says the platform operator is an independent product; Agent 1 recommends (b).
4. **Public/marketing surface.** Is the pilot allowed to have a public landing + sign-in UI only (no marketing site), or is a thin `(public)/*` surface in scope for this transformation? Agent 1 recommends authenticated-only for now; public can follow once the brand is stable.
5. **Typeface.** The brief implies a premium identity (champagne gold, charcoal). Confirm: (a) a premium display serif + a neutral humanist sans (e.g. Fraunces + Inter / IBM Plex Sans), or (b) a single refined sans (e.g. Söhne-alike / Geist)? [Assumption needed by Agent 2.]
6. **Ekklesia logo & brand assets.** Who produces them? (Agent 2 can only token-ise what exists.) If not yet produced, Phase 2 should include a placeholder mark + a note in `docs/ekklesia/design-tokens.md` that logo assets are deferred.
7. **i18n timing.** `docs/AGENTS.md` mandates EN + SW. Do Agents 4–5 route all strings through an i18n helper from day one, or defer to a dedicated i18n pass? Agent 1 recommends day-one `t()` calls with keys even if the SW translations lag.
8. **Dev-auth headers.** OK for Agent 3 to ship a single `apiFetch()` helper that reads headers from `localStorage` + `ALLOW_DEV_AUTH=1` build flag, so no component hardcodes IDs? Current `/events` + `/platform` do.
9. **Role list for navigation groups.** Confirmed roles today: `church_administrator`, `member`, `finance_officer`, `platform_operators`. Are `pastor`, `ministry_leader`, `finance_committee`, `data_steward` also expected nav personas in Phase 4, or only `member` + `church_administrator` for pilot?
10. **Component library imports.** Is there any appetite for using an off-the-shelf headless library (Radix Primitives / React Aria) under our styled wrappers for dialogs, menus, and selects, or are we writing everything from scratch? Agent 1 recommends Radix Primitives for dialogs/menus/popovers only, to avoid re-inventing focus management; everything else stays ours.
